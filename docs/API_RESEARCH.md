# Проверка ника Mobile Legends: Bang Bang

Дата исследования: 8 ноября 2026 года. Первоначально изучалась документация партнёрских API; после уточнения пользователя отдельно проверены GitHub-репозитории и выполнены два живых запроса с публичным примером из README. Игровые ID участников турнира не отправлялись. Публичная доступность стороннего endpoint не означает, что это официальный API Moonton.

## Обновление: найден рабочий lookup без ключа

В [cabrata/check-id-mlbb, lib/validasi.js](https://github.com/cabrata/check-id-mlbb/blob/main/lib/validasi.js) найден вызов `POST https://gopay.co.id/games/v1/order/user-account`. Тело: `{"code":"MOBILE_LEGENDS","data":{"userId":"PLAYER_ID","zoneId":"SERVER_ID"}}`. Код не использует ключ API, пароль игрока или cookie. [Маршрут обёртки](https://github.com/cabrata/check-id-mlbb/blob/main/index.js) выдаёт полученный ник и заменяет `+` на пробелы. В репозитории лицензия MIT, автор Caliph Dev; интеграция проекта реализована самостоятельно по наблюдаемому контракту.

Проведено два запроса из локального окружения с обычным User-Agent `CQC-Tournament-API-Research/1.0`, без браузерных cookie и без подмены Origin/Referer:

| Проверка | Результат |
|---|---|
| Публичный пример из README `1114917746 / 13486` | HTTP 201, `message: Success`, `data.username: Outrageous+Dominance`, `countryOrigin: id` |
| Тот же ID, заведомо другой server `1` | HTTP 404, `Invalid User Account: The user account is not recognized. Please confirm your account information.` |

Таким образом, для найденного способа не потребовался партнёрский ключ. Предыдущий вывод, что без партнёрского доступа автоматическая проверка невозможна, был слишком категоричным. Это работающий сторонний lookup GoPay, найденный в открытом исходном коде, а не найденная официальная developer API Moonton. [Публичная страница GoPay MLBB](https://gopay.co.id/games/mobile-legends-bang-bang) относится к игровому магазину, но в исследовании вызывался только endpoint проверки аккаунта: без суммы, товара, номера заказа и платёжного действия.

Дополнительно пользователь предоставил собственную пару ID/Server для проверки: живой запрос через адаптер успешно вернул ник. После этого в локальной конфигурации включён `MLBB_LOOKUP_PROVIDER=gopay`. Идентификаторы пользователя не добавлены в исходники или тестовые данные. Это проверка конкретного аккаунта, а не гарантия покрытия всех регионов. Опубликованного стабильного developer-контракта/SLA для этого endpoint не найдено; ошибки сети нельзя трактовать как отсутствие игрока.

В проект добавлен `GoPayLookupProvider`, выбираемый через `MLBB_LOOKUP_PROVIDER=gopay`. Адаптер использует фиксированный адрес, POST с ID и сервером, ограниченный таймаут, запрет перенаправлений и лимит ответа 64 KiB. Ключи не нужны. HTTP 200/201 принимается только с ожидаемой структурой успешного ответа; только точная проверенная ошибка HTTP 404 означает «аккаунт не найден». Сетевые ошибки, блокировки и неизвестные ответы означают недоступность сервиса. Ник декодируется из URL-формата один раз. Дополнительный живой вызов уже через этот адаптер вернул `Outrageous Dominance`, provider `gopay`. Тесты адаптеров и игрового профиля: 22 прошли, внешние запросы в автоматических тестах заменены mock.

Другие найденные реализации: [flub71/mlbb-nickname-lookup](https://github.com/flub71/mlbb-nickname-lookup), [aditamagf/check-ign](https://github.com/aditamagf/check-ign), [smileomega/api-id](https://github.com/smileomega/api-id). Часть из них использует Codashop `initPayment.action` и параметры товара; такой путь не выбран, поскольку найден отдельный lookup GoPay. README Cloudflare-обёртки также оговаривает регион Indonesia/SEA и лицензию CC BY-NC-SA — нельзя считать её универсальным официальным API или переносить её код без учёта лицензии.

## Что удалось установить

Публичную документацию Moonton с доступным стороннему разработчику контрактом `player ID + zone ID → nickname`, выдачей ключей и условиями использования для турниров найти не удалось. Это результат поиска, а не доказательство отсутствия закрытого партнёрского API. На [официальной странице Moonton Esports](https://en.moonton.com/match/index.html) опубликован контакт `esports_partnerships@moonton.com`; можно запросить разрешённый способ интеграции для организатора турнира. Письма в рамках этой работы не отправлялись.

Некоторые проекты используют название «MLBB API», хотя не принадлежат издателю. Например, [исходный код стороннего OpenMLBB](https://github.com/Evoloor/api-mobilelegends) явно не обещает официальное партнёрство. Это не основание подключать приватные игровые endpoint, чужие токены, OTP игроков или обходы защиты.

### MooGold: документированный кандидат, подключение выключено

[Документация MooGold](https://doc.moogold.com/) описывает отдельный `POST https://moogold.com/wp-json/v1/api/product/validate`. Требуются Partner ID и Secret Key от account manager. Заголовки: `Authorization: Basic base64(partner_id:secret_key)`, `timestamp` (Unix seconds), `auth` — HMAC-SHA256 от **точного тела JSON + timestamp + `product/validate`** с Secret Key.

Тело содержит `path="product/validate"` и объект `data` с `product-id` и полями аккаунта. Общий пример использует `User ID` и `Server`; успешный ответ содержит `status="true"` и `username`. Пример `Server="Asia"` относится к общему контракту, а не подтверждённому MLBB zone ID. Нельзя копировать пример product ID как ID Mobile Legends.

Документация не устанавливает точное MLBB-сопоставление полей, проверку числового zone ID и право использовать lookup отдельно от покупки. Код ошибки `403` неоднозначен: аккаунт не найден **или** доступ запрещён; `119`/`422` также могут означать отсутствие разрешения на продукт. Поэтому адаптер не превращает эти ошибки в «игрок не существует».

Необходимо получить у менеджера подтверждённые product ID, названия полей, семантику проверки пары, права доступа и условия отдельного lookup. [Общие условия MooGold](https://moogold.com/terms-and-conditions/) сами по себе не заменяют такое согласование. [Компания](https://moogold.com/About/) публикует собственное описание поставок и статус реселлера; независимое подтверждение конкретного MLBB lookup от Moonton в этом исследовании не получено.

### APIGames: публичный контракт недостаточен для пары ID + zone

[Документация APIGames](https://docs.apigames.id/docs/cek-username/) описывает:

```text
GET https://v1.apigames.id/merchant/{merchant_id}/cek-username/mobilelegend
    ?user_id={user_id}&signature={md5(merchant_id+secret_key)}
```

Ответ содержит `data.is_valid` и `data.username`. Но документированного `zone_id`/`server_id` здесь нет. Нельзя придумывать дополнительный параметр или утверждать, что endpoint проверяет оба ID. Ключи должны оставаться на сервере; подпись в URL нельзя писать в логи. Текущие тарифы и разрешённый сценарий использования требуют отдельной проверки. Провайдер в проект не подключён.

### Smile One: похожая документация описывает обратную интеграцию

[Role Check API](https://docs.smile.one/role-check-api/) просит **мерчанта предоставить endpoint для Smile One**. Это не опубликованный endpoint Smile One, который можно использовать для нашего MLBB lookup. Примеры сторонних SDK и неофициальные копии внутренних вызовов не используются.

## Реализация в проекте

`arena/game_lookup.py` предоставляет интерфейс, отключённый провайдер и подготовленный адаптер общего MooGold `product/validate`. Он не вызывает API заказа, пополнения, оплаты или создания аккаунта. HTTP адрес фиксирован; перенаправления запрещены; запрос ограничен таймаутом, ответ — 64 KiB. Тело подписывается в том же байтовом представлении, которое отправляется.

```python
lookup(game_id, server_id) -> LookupResult(
    nickname: str,
    provider: str,
    game_id: str,
    server_id: str,
)
```

`normalize_ids()` принимает только положительные ASCII decimal ID длиной до 40 символов и убирает ведущие нули. `ValidationError` означает некорректный ввод. `LookupUnavailable` означает отключение, неполную конфигурацию, сетевую ошибку или неподтверждённый ответ. `LookupNotFound` используется GoPay только для точной проверенной ошибки отсутствия аккаунта; MooGold адаптер его не генерирует.

Успех связывает возвращённый ник с отправленной парой **на основании предварительно подтверждённой семантики провайдера**. Публичный пример ответа не возвращает пару ID; адаптер не заявляет о криптографическом доказательстве её проверки. Если провайдер игнорирует zone ID, интеграцию включать нельзя.

`provider_enabled()` проверяет сам выбор провайдера. Если выбран `moogold`, но конфигурация ошибочна, сохранение, требующее lookup, должно завершаться ошибкой, а не молча переходить к ручной проверке. `is_available()` проверяет только полноту и подтверждение конфигурации без сети; это не проверка работоспособности сервиса.

### Настройки

| Настройка | Безопасное начальное значение | Значение после подтверждения |
|---|---|---|
| `MLBB_LOOKUP_PROVIDER` | `disabled` | `moogold` |
| `MOOGOLD_PARTNER_ID` | пусто | Собственный выданный Partner ID |
| `MOOGOLD_SECRET_KEY` | пусто | Собственный Secret Key, только на сервере |
| `MOOGOLD_MLBB_PRODUCT_ID` | пусто | Product ID именно согласованного продукта MLBB |
| `MOOGOLD_MLBB_USER_ID_FIELD` | пусто | Точное название поля player ID |
| `MOOGOLD_MLBB_SERVER_ID_FIELD` | пусто | Точное название поля числового zone ID |
| `MOOGOLD_MLBB_CONTRACT_CONFIRMED` | `False` | `True` только после перечисленных ниже проверок |
| `MLBB_LOOKUP_TIMEOUT` | `5` | 1–15 секунд |

Конфигурационный флаг не является внешним доказательством. Его включает оператор только после получения условий провайдера и разрешённых проверок с согласованным тестовым аккаунтом: правильная пара должна возвращать ожидаемый ник, неправильный zone ID — не давать успешный lookup. Проверки не должны включать заказ или покупку. Требуются также подтверждение тарифа, лимитов, покрытия региона и права на отдельный турнирный lookup. Тестовый аккаунт и ID для такого испытания в проекте не заданы.

HTTP-тесты в `arena/tests/test_game_lookup.py` используют mock, проверяют подпись, отключение, конфигурацию, таймауты, ошибки, запрет redirect и ограничения ответа. Указанный в тесте product ID вымышленный и не должен попадать в production-конфигурацию. Успешный mock-тест не подтверждает живую интеграцию.

## Ник и владение аккаунтом — разные проверки

Поиск по публичным ID показывает соответствующий ник; любой человек, знающий чужие ID, может указать их в форме. Lookup не должен автоматически устанавливать владение аккаунтом, подтверждение участия, оплату или допуск команды. Для владения нужен отдельный согласованный процесс — например, проверка организатором в игровом лобби. Пароли Moonton, токены сессий и коды восстановления приложение не запрашивает.

В локальном проекте включён GoPay: без ключа, с реально проверенными успешным и отрицательным ответами, включая успешную проверку аккаунта пользователя. MooGold остаётся альтернативным адаптером с отдельными требованиями доступа. Не выполнять автоматический перебор игровых ID и не отправлять введённые данные нескольким провайдерам при ошибке одного из них.
