## Следующая доработка для одного турнира

После дополнительного цикла реализации полный набор **194 теста прошёл**. Закрыты оставшиеся технические сценарии P1-03/P1-04/P1-05 и P2-01/P2-02 в рамках одного турнира:

- Капитан отзывает ожидающую проверки заявку на редактирование, исправляет реквизиты и неоплаченные роли, обновляет приглашение, подаёт заново. Старый invite отзывается.
- Организатор архивирует участника для замены до конца регистрации/сетки. Даже оплаченный старый участник сохраняет личную страницу, владельца и финансовую историю; новая заявка получает отдельный взнос. Свободного переноса чужих денег нет.
- Спор о занятом игровом ID проходит приватное обращение и проверку организатором в игре. Одноразовое решение содержит причину/автора/дату. Активные участия блокируют перенос профиля до отдельного разбора; архивная финансовая история не меняется. Lookup по-прежнему не является доказательством владения.
- Историческое участие само по себе больше не блокирует редактирование игрового профиля.
- Telegram показывает безопасные промежуточные этапы входа без раскрытия личности до подтверждения.
- Поддерживается неполная double-elimination сетка с явными свободными проходами без фиктивных поражений.

Границы сохранены намеренно: нет автоматических возвратов/переноса взноса, правок сыгранного результата, изменений состава после блокировки регламентными сроками, рейтингов и управления несколькими турнирами. Окончательные условия и публикация не подменяются тестовыми настройками. Версионирование личного согласия с изменяемым регламентом пока не автоматизировано.

## Метод и уровень доказательств

Проверены модели, маршруты, формы, сервисы, шаблоны, JS и админка. Для основных дефектов выполнен отдельный Python/Django-прогон с `setup_databases`/`teardown_databases`, `Client`, пользователями и командами только во временной тестовой БД. Внешний lookup отключён в тесте; реальные внешние запросы и сообщения не отправлялись. Для проверки блокировки исправлений использовались реальные сервисы и права ModelAdmin, включая superuser.

Полноценный визуальный браузерный аудит недоступен: инструмент CUA сообщил, что browser access host недоступен. Поэтому ниже нет выдуманных утверждений о мобильном переполнении, неработающих кликах или визуальных размерах. UI-находки основаны на фактическом контексте Django и шаблонах. Недоступность браузера не помешала воспроизвести серверные тупики.

Приоритеты: **P1** — основной пользовательский сценарий или восстановление заблокированы; **P2** — существенный операционный/UX-недостаток; **ограничение** — известная граница текущей реализации, которую нельзя выдавать за неожиданную уязвимость. P0 по проверенным путям не найдено.

## P1-01. Команду невозможно создать до заполнения состава

**Тип:** несоответствие основному требованию пользователя; подтверждено исполнением.

`register_team(..., players=[])` возвращает `Добавьте игроков команды.`; затем сервис требует ровно `roster_size` основных игроков. В форме капитан заполняет ник, Game ID и Server ID каждого. В модели нет общего приглашения, а в маршрутах — вступления в команду; есть только UUID уже созданного Participant.

**Воспроизведение:** войти как капитан с Telegram, открыть регистрацию, попытаться создать команду с названием/контактом без готовых игровых данных всей пятёрки. Создание не проходит. Изолированный вызов сервиса подтвердил отказ даже для тестового состава из одного игрока.

**Последствие:** игрок не может самостоятельно занять ещё не созданное место. Капитан обязан собирать и перепечатывать чужие данные, а «приглашение» появляется только после завершения этой работы.

**Исправление:** отделить черновик команды от заявки на турнир; добавить общую отзываемую ссылку и self-join. Полный основной состав проверять при подаче, а не при создании команды. Ручной ввод оставить дополнительным действием.

**Код:** `arena/services.py:77`, `arena/forms.py:player_formset`, `arena/views.py:register`, `arena/urls.py`, `arena/models.py:Team`.

## P1-02. У вошедшего игрока нет кабинета его команды

**Тип:** функциональная ошибка навигации; подтверждено HTTP и контекстом.

`captain()` ищет только `Team.captain=request.user`. Участие через `Participant.account` не учитывается. После обычного входа пользователь с уже заполненным GameAccount без сохранённого return-token направляется именно в этот кабинет.

**Воспроизведение:** создать команду одного пользователя, привязать место к другому через `claim_participant`, войти вторым и открыть `/captain/`. Получено **HTTP 200, `context['team'] is None`**, хотя `Participant.objects.filter(account=member, team=team).exists()` равно `True`.

**Последствие:** действующий игрок получает сообщения «Ваша будущая команда» и «Команда ещё не создана», предложение заявить новую команду. Он не находит свой взнос и место без сохранённой персональной ссылки.

**Исправление:** общий личный кабинет с разделами «Моё участие» и «Управляю командой». Возвращать игрока к существующему участию после входа; капитанский функционал показывать по роли, а не считать всех посетителей капитанами.

**Код:** `arena/views.py:114`, `arena/telegram_auth.py:auth_finish`, `templates/arena/captain.html`.

## P1-03. Ошибку капитана в Game ID/Server ID нельзя исправить через продукт

**Тип:** тупик восстановления; подтверждено кодом и правами админки.

`claim_participant` требует полного совпадения ID/сервера с заранее внесённым местом. При несовпадении шаблон предлагает обратиться к капитану. Однако капитану не предоставлены изменение, удаление или замена участника; ParticipantAdmin наследует ReadOnlyAdmin и запрещает изменение даже superuser.

**Воспроизведение:** капитан вносит одну неверную цифру, игрок сохраняет правильный профиль и пытается подтвердить участие. Сервис отклоняет привязку. Капитан открывает кабинет — действия исправления нет; `ParticipantAdmin.has_change_permission(superuser, player)` возвращает **False**.

**Последствие:** одна опечатка останавливает допуск всей команды. Совет интерфейса ведёт к человеку, у которого нет инструмента исправления. SQL/Django shell не являются пользовательским восстановлением.

**Исправление:** до подачи — исправление/удаление чернового места; после подачи — контролируемая замена с журналом, пересмотром проверки состава и явной политикой уже поступивших платежей. Не разрешать произвольное редактирование подтверждённых финансовых записей.

**Код:** `arena/game_accounts.py:179`, `arena/admin.py:12`, `arena/admin.py:54`, `templates/arena/participant.html`.

## P1-04. Отклонение команды необратимо, но её состав продолжает занимать ID

**Тип:** ошибка жизненного цикла; подтверждено исполнением.

**Воспроизведение и фактический результат:**

| Действие после `team.status='rejected'` | Результат |
| --- | --- |
| Капитан открывает `/register/` | HTTP 302 → `/captain/` |
| Повторно вызывает регистрацию своей исправленной команды | `У капитана уже есть команда в этом турнире.` |
| Другой капитан пытается включить прежнего игрока | `Игрок с таким Game ID и Server ID уже зарегистрирован.` |
| Организатор вызывает `confirm_team` после исправления ситуации | `Отклонённую команду нельзя допустить без пересмотра заявки.` |

При этом действия «пересмотреть/открыть заново» нет, а TeamAdmin/ParticipantAdmin только читают. Свободное место в счётчике не означает освобождения игрока или восстановления капитана.

**Последствие:** нельзя исправить обычный отказ или перейти в другую команду штатными средствами. Формулировка сервиса обещает пересмотр, которого продукт не предоставляет.

**Исправление:** явные reopen/resubmit/withdraw и переходы членства. Отклонённая заявка должна хранить историю, но не бессрочно блокировать действующее членство. Изменения проводить транзакционно, с разграничением ролей и сохранением платежей/аудита.

**Код:** `arena/views.py:88`, `arena/services.py:84`, `arena/services.py:240`, ограничения в `arena/models.py:109` и `arena/models.py:128`.

## P1-05. Публичную пару игровых ID можно занять без доказательства владения, а оспорить нельзя

**Тип:** подтверждённая возможность блокирования чужого профиля; не утверждение о взломе MLBB.

Lookup проверяет существование ника для пары ID/Server, что корректно оговорено в UI; он не доказывает владение. `GameAccount` делает эту пару глобально уникальной. Достаточно собственного Telegram, известной публичной пары и галочки самоутверждения, чтобы первым занять её. Действительный владелец затем получает отказ. GameAccountAdmin не позволяет организатору изменить привязку.

**Воспроизведение:** два разных пользователя с Telegram; первый сохраняет публичную пару, второй сохраняет ту же пару. Второй получает `Эти идентификаторы уже заявлены в другом профиле. Обратитесь к организатору.` Изолированная проверка выполнила этот сценарий в поддерживаемом ручном режиме; в режиме lookup проверка уникальности та же, а lookup по собственному контракту не доказывает владение. `GameAccountAdmin.has_change_permission(superuser, profile)` равно **False**.

**Последствие:** отказ в регистрации законному игроку, включая случай неверного первого ввода. Оговорка «это не доказательство владения» честна, но не устраняет эффект глобальной блокировки.

**Исправление:** ограничить силу предварительной привязки; предусмотреть спор и восстановление организатором с доказательством в игре, журналом и пересмотром связанных заявок. Не переносить подтверждённые платежи на другой аккаунт автоматически. При необходимости добавить реальное подтверждение владения отдельным механизмом.

**Код:** `arena/game_accounts.py:87`, `arena/game_accounts.py:102`, `arena/models.py:315`, `arena/admin.py:99`.

## P2-01. Игровой профиль блокируется навсегда по наличию любого участия

**Тип:** слишком широкое ограничение редактирования; подтверждено исполнением.

`Participant.objects.filter(account=user).exists()` блокирует весь профиль без проверки состояния команды/турнира. Воспроизведено после отклонения команды: попытка изменить профиль возвращает `Профиль уже связан с составом. Изменения согласуйте с организатором.` Через админку согласованное изменение выполнить нельзя (P1-03/P1-05).

**Последствие:** нельзя исправить ник, обновить сведения или сменить игровой аккаунт после прекращения участия. Блокировка полезна для активного состава, но область её действия бессрочна.

**Исправление:** определить активные состояния, разделить профиль и снимок игровых данных в заявке, добавить контролируемое исправление. Данные сыгранного состава не переписывать вслед за редактированием профиля.

**Код:** `arena/game_accounts.py:100`, `arena/game_accounts.py:128`.

## P2-02. Telegram-вход требует несколько ручных переходов и не показывает промежуточное состояние

**Тип:** проверенная структура UX; не найденная уязвимость.

Пользователь открывает бота, отвечает шестизначным кодом, отдельно нажимает подтверждение в боте, возвращается в браузер и ещё раз подтверждает показанную личность. В браузере состояния после открытия бота и после принятия кода остаются одинаковыми `pending`; отслеживание проверяет только переход в `ready`.

**Последствие:** пользователь, отправивший код, может считать действие законченным и ждать без понимания оставшегося подтверждения. Вход безопаснее случайного принятия пересланной ссылки, поэтому удалять проверки без альтернативной защиты нельзя.

**Исправление:** показать безопасные промежуточные статусы «Бот открыт» / «Код принят — нажмите подтверждение в Telegram» без раскрытия личности до согласия; кратко перечислить все шаги заранее. Для опубликованного HTTPS-сайта отдельно оценить официальную Telegram-авторизацию с эквивалентными защитами, а не заявлять, что сейчас она подключена.

**Код:** `arena/telegram_auth.py:auth_state`, `arena/telegram_auth.py:handle_auth_update`, `templates/arena/telegram_auth.html`, `static/arena/app.js`.

## Явные ограничения, не маскируемые под найденные баги

- **Сетка:** поддерживается полный состав из степени двойки; при 15 готовых командах из 16 генерация откажет. Это прямо заложено в `arena/bracket.py:23`, а не скрытая поломка алгоритма. Нужна заранее выбранная политика недобора/неявки: byes, сокращение, резерв или отмена. Менять размер на любое число нельзя — модель разрешает только поддерживаемые размеры.
- **Локальные приглашения:** JS копирует ссылку с `window.location.origin`. При запуске на `127.0.0.1` или `localhost` такая ссылка не откроет сайт на телефоне другого игрока. Для локального демо это нормально, для реального набора команды нужен доступный адрес и HTTPS. Сама новая invite-модель этого не решит.
- **Возвраты:** исходящая операция возврата и её статус не моделируются. Подтверждённое поступление — история получения денег, а не автоматически актуальный баланс. Нельзя выдавать общую сумму подтверждений за сумму после возвратов.
- **MLBB ownership:** найденный ник не является доказательством владения. Не следует переименовывать lookup в «верификацию владельца».
- **Визуальная QA:** отсутствие интерактивного браузера означает, что адаптивность и клики здесь не сертифицированы.

## Что проверено и не признано дефектом

Существующие механизмы ограничивают финансовое подтверждение сотрудником/назначенным кассиром; пользовательская отметка оплаты не подтверждает банк. В прежнем интеграционном прогоне проверялись CSRF, запрет изменяющего GET, доступ обычного пользователя, уникальный банковский номер, повторные/устаревшие решения и отдельное подтверждение Telegram-личности. Эти защиты нужно сохранить при переработке. Факт прохождения таких тестов не закрывает перечисленные продуктовые тупики.

## Приоритет переработки и приёмка

Сначала P1-01/P1-02: создать неполную команду, получить общую invite-ссылку, принять самостоятельного игрока и показать его реальное участие в кабинете. Одновременно заложить восстановление P1-03/P1-04, иначе новые приглашения унаследуют старые необратимые состояния. До реальной регистрации людей нужен разбор конфликта игровых аккаунтов P1-05.

Приёмочные сценарии:

1. Капитан создаёт команду без чужих игровых данных; приглашение работает у нового пользователя.
2. Один пользователь не занимает два места турнира, повторный join идемпотентен, отозванная ссылка не работает.
3. Последнее свободное место при двух одновременных join получает только один игрок.
4. Капитан при желании добавляет черновое место вручную; игрок подтверждает его собственным профилем, а опечатку можно исправить.
5. После обычного повторного входа игрок видит свою команду, взнос и следующий шаг.
6. Отказ заявки содержит причину и реальный путь исправления/повторной подачи.
7. Уход/замена до блокировки состава освобождает активное место, но не удаляет финансовую историю.
8. После допуска/старта замены ограничены регламентом; старые приглашения и снимки решений не меняют новую заявку.
9. Организатор имеет контролируемый, журналируемый инструмент разрешения спора за игровой ID.
10. Денежные проверки, Telegram-login CSRF и неизменяемый аудит продолжают проходить тесты.

Это отчёт о конкретном снимке. После изменений каждый пункт нужно перепроверить и отметить исправленным отдельно; появление новой формы не является доказательством устранения всего жизненного цикла.
