# PostgreSQL и общий лимитер запросов

Подготовлено 8 ноября 2026 года. Проведены отдельные проверки SQLite и реального PostgreSQL в изолированном проекте Supabase. Активная схема приложения не использовалась для тестов.

## Изменения

- Миграция `0008_rate_limit_bucket` создаёт общие для всех экземпляров приложения счётчики. Применить обычной командой `python manage.py migrate` до запуска новой версии.
- Для POST сохранены лимиты: 20 запросов за 15 минут для входа/регистрации/`/auth/`, 120 за минуту для остальных действий. Отдельные адреса и категории имеют отдельные окна. В базе хранится HMAC адреса, а не исходный IP. Лимитер не зависит от локального кэша или жизни serverless-процесса. При ошибке базы действие не выполняется, ответ — 503.
- Только точный `/telegram/webhook/` исключён из пользовательского лимитера: у Telegram общий исходящий IP. Этот обработчик сам проверяет секрет, размер тела, повтор обновления и блокировку обработчика.
- `RATE_LIMIT_TRUST_VERCEL_IP=True` допустим только за доверенной инфраструктурой Vercel. Используется валидный одиночный `X-Vercel-Forwarded-For`; при отсутствии/ошибке — общая категория неизвестного адреса. В обычном локальном запуске используется `REMOTE_ADDR`; произвольный `X-Forwarded-For` игнорируется. [Документация заголовков Vercel](https://vercel.com/docs/headers/request-headers#x-vercel-forwarded-for).
- `python manage.py purge_rate_limits` удаляет не более 1000 истёкших счётчиков за запуск, не затрагивая действующие. Команду можно включить в обычное периодическое обслуживание. Активный адрес повторно использует прежнюю строку.

## Транзакции

Блокировки результата и редактирования матча ограничены строкой самого матча через `select_for_update(of=('self',))`: nullable-ссылки источников сетки остаются читаемыми. PostgreSQL запрещает блокировать nullable-сторону outer JOIN. Аналогично запрос кассира блокирует платёж без неявной блокировки связанных команды/участника. [Правила Django для select_for_update](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update).

Изменения состава соблюдают порядок «турнир → команда → пользователь → игровой профиль → участник → платёж», пропуская ненужные строки. Создание/изменение профиля блокирует существующую строку пользователя, даже когда профиль ещё не создан. Споры об аккаунте блокируют пользователей и профили по возрастанию PK. Сохранение условий турнира повторно проверяет ограничения после блокировки турнира. HTTP-проверка игрового профиля остаётся вне транзакций.

Существующие уникальные ограничения остаются последней защитой: профиль пользователя, пара игровых ID, платёж участника, банковская операция, запись лимитера. Конфликты банковской операции/привязки обрабатываются через вложенную транзакцию с откатом до savepoint. Создание первого счётчика использует уникальный PK и `get_or_create` под блокировкой.

## Проверка перед production

Целевой SQLite-прогон: 92 теста, 91 успешный и 1 пропущенный PostgreSQL-тест конкурентного лимита.

В реальном PostgreSQL прошли 15 выбранных тестов, без пропусков: восемь конкурентных первых запросов лимитера (ровно три разрешённых), конкурентная обработка одного Telegram update, повтор обновления и кода входа, отсутствие HTTP внутри транзакции, платежи/уникальный банковский номер, лимит команд и допуск, запись результата и редактирование расписания с nullable-источниками, ожидание незавершённого источника сетки. В первом запуске была опечатка имени класса одного web-теста в локальном QA helper; этот тест исправлен и успешно выполнен отдельно. Ошибок приложения не обнаружено.

Оба запуска создавали отдельные базы `test_cqc_<UUID>` штатным Django test runner с применением миграций до `0008`. Supabase pooler удерживал серверные соединения после закрытия клиентских, из-за чего обычный `DROP DATABASE` возвращал `ObjectInUse`. Очистка выполнена только для точных имён созданных временных баз после проверки их владельца, через `DROP DATABASE … WITH (FORCE)`; отсутствие обеих баз подтверждено. QA helper содержит такой же узкий fallback для кода PostgreSQL `55006`. Временные базы удалены; production-схема не изменялась.

Не направлять тесты на активную базу или общую рабочую схему. Полный набор по сети и нагрузочные проверки не запускались. Этот результат подтверждает выбранные сценарии совместимости, но не является проверкой реальной доставки Telegram webhook или запуском приложения в Vercel.
